= Camera Preview and Selective Frames

== Current scope

The camera button is an opt-in live preview. It starts off on each launch and shows the camera feed inside its amber circular border while enabled. Clicking it again stops the tracks, clears the preview and discards the retained frame. Microphone capture remains independent; this camera stream requests no audio.

In Unmute mode, selected snapshots are analysed by the configured local Ollama model (`LOCAL_VISION_MODEL`, falling back to the voice `LLM_MODEL`). The installed Qwen alias supports images. The selected JPEG and its capture timestamp are supplied through validated `scene_data`. The voice model receives the actual image as an ephemeral multimodal user-data message next to the current question. Images are never appended to conversation history. Camera ON/OFF is supplied separately as trusted device state, so pending or expired images do not imply the camera is off. Nod.ie can answer questions about that snapshot. No new model stays loaded solely for vision, and no images are saved to disk. See https://docs.ollama.com/capabilities/vision[Ollama vision API].

Recent face matches are supplied to Unmute conversation as uncertain observations; they never establish who spoke. Reverie observation writes are not connected. Local batch voice supplies the actual selected JPEG directly to its image-capable conversational model; see the local voice section below. A frame description is untrusted reference data, never a command, identity proof, or authority for a memory write. Camera-off immediately clears retained snapshots; Unmute snapshots expire after 75 seconds and local voice snapshots after ten seconds. The desktop does not persist camera-on across restarts.

== Selection policy

When the conversation processing gate permits, every 250 ms compare a 64 by 48 pixel image locally on the CPU. Compare against the last selected frame so gradual changes can accumulate. Compensate for a median luminance shift to suppress near-uniform exposure changes; ignore small channel differences. An initial threshold requires at least 8% of pixels to change substantially, with a minimum average difference.

Wait 500 ms for the scene to settle, or at most 2.5 seconds during continuous movement. Automatic selections have a five-second cooldown. Refresh an unchanged scene every 60 seconds. The `requestFrame()` API selects immediately when the camera is already enabled; it never turns on an off camera. Each incoming transcription requests a fresh snapshot, limited to one image update every two seconds.

Capture requests 1280 by 720 pixels at at most 10 fps, with camera-supported fallback. The change detector still uses only 64 by 48 pixels. Only selected frames are encoded as JPEG, bounded to 768 by 576 pixels and 512 KB. The current UI retains the latest JPEG in memory. Image updates have a two-second minimum interval and no model inference is required to supply them to the conversation. Face matching shares selected frames. Separately, the event journal runs structured vision on selected frames at most once every 15 seconds, after five seconds without voice activity, with a three-second deadline, 320-token output budget and 32 KB response limit. It is cancelled by speech. These limits bound work but do not guarantee latency on a shared model.

Pixel changes are triggers, not a judgement of interest or danger. Small or brief events can be missed; illumination changes and camera movement can still cause false triggers. Any home-awareness notifications need separate validation, repeated confirmation and notification cooldowns. This is not an alarm system.

== Validation

Unit tests cover unchanged scenes, sensor noise, brightness shifts, object arrivals, transient movement, continuous motion, cumulative changes, cooldowns, refreshes, explicit requests, camera permission races, late JPEG completion and analysis backpressure. A Chromium fake-camera check verifies the button preview, selected JPEG generation, absent camera audio and stopped tracks when disabled.

== Scene-data transport and tool isolation

Re-run `python3 unmute-service/prepare-backend.py /path/to/unmute` and recreate the backend with `compose.override.yml` to install the extended session schema and handler. Older backends ignore the new field and cannot describe snapshots; they do not receive scene text as policy.

Scene text never enters the system instructions. Once a session receives a snapshot, its tool advertisement and execution are disabled for the rest of that connection, including after the camera is switched off, because earlier replies may retain visual content. Start a fresh voice connection with the camera off to restore memory tools. This deliberately limits camera-assisted conversation to spoken answers; visual content cannot authorize memory queries or writes.

Camera startup, including an unanswered permission request or stalled video playback, has a ten-second deadline. Cancelling startup settles immediately and stops any stream that arrives later.

== Local face recognition

Face recognition is separate from Qwen scene descriptions. The desktop sends selected JPEG frames to a persistent, single-threaded CPU worker using OpenCV YuNet (2023 model) and SFace. Models are pinned to OpenCV Zoo revision `47534e27c9851bb1128ccc0102f1145e27f23f98`, with SHA-256 and byte-size verification. YuNet is MIT licensed; SFace is Apache-2.0 licensed. Upstream sources: https://github.com/opencv/opencv_zoo/tree/47534e27c9851bb1128ccc0102f1145e27f23f98/models/face_detection_yunet[YuNet] and https://github.com/opencv/opencv_zoo/tree/47534e27c9851bb1128ccc0102f1145e27f23f98/models/face_recognition_sface[SFace].

Recognition is disabled by default and requires the camera to be on. Frames reuse the current vision selection and quiet-period policy. No additional camera is opened. Input is capped at 512 KB and 1280 by 960 pixels, inference at three seconds, output at 128 KB, and processing at one request with no backlog. At most eight sufficiently large and sharp faces are analysed per frame; small/blurry faces are skipped. The worker uses no GPU. Images are never written to disk or sent to an external recognition provider.

Settings > People — faces supports enable, rename, forget and merge. Local embeddings are kept in `~/.config/nodie/recognition/faces.json`, with owner-only file permissions, atomic writes and locking. At most 32 profiles and four samples per profile are retained. Unknown runtime candidates remain in memory for at most 90 seconds without a match; confirmation creates a named profile that remains until removed. Legacy unnamed saved profiles expire after seven days. Disabling stops collection but preserves profiles; Forget all deletes profiles and disables recognition. Clear conversation history does not delete these profiles. Disabling, editing or deleting invalidates in-flight matches.

The initial thresholds are conservative engineering defaults, not calibrated household accuracy guarantees. Ambiguous matches remain unnamed. A face match does not establish who is speaking, grant device access, or authenticate a person. Photos and screens may also match; no liveness detection is provided.

python3 scripts/setup-face-models.py
node --test tests/unit/face-recognition.test.js

Local face extraction, matching, selected-frame collection, profile management and typed uncertain observations into Unmute are connected. An explicit introduction opens a temporary face-selection panel in Settings. Select an isolated face crop from the captured frame, check the name spelling, then confirm. Several eligible faces require an explicit selection; named or uncertain profiles cannot be relabelled through this introduction. A face that disappears, becomes uncertain or belongs to an expired proposal cannot be saved. Crops with another detected face overlapping them are excluded from selection. Photos, posters and screens can contain detectable faces: these crops do not establish liveness or authenticate someone. Household recognition accuracy still needs live calibration and testing.

== Direct image questions

Unmute no longer waits for a separate two-sentence scene summary. Selected JPEGs remain capped at 512 KB, 768×576 and 85% quality. Spoken input requests a fresh frame at most once every two seconds; scene changes still pass through the local frame selector. Only the latest image is retained in memory, expires after 75 seconds on both sides, and is removed when the camera is disabled. The separate journal observation pass can briefly compete for the shared model before cancellation. This is snapshot-based visual question answering, not continuous arrival/departure tracking or proactive room narration.

After an image is supplied, model-directed memory tools remain disabled for that connection. Independent person recall is permitted only from microphone transcript text; image text cannot trigger it.

=== Daily observations and fullscreen debug

The desktop records a separate, text-only event journal with 30-day retention by default, a 6,000-event ceiling, and Settings controls to inspect or clear it. No images, audio, embeddings or full conversation transcripts are stored in this journal. Introduction crops stay in memory, are bounded to eight 96×96 JPEGs, and are cleared from the selection panel after confirmation, cancellation, expiry or closing Settings. They are not written into recognition profile files or sent to the voice model. Recognition remains opt-in; enabling the journal does not enable a camera, microphone, face recognition or speaker recognition. Face and voice observations remain uncertain matches. Naming a profile records the confirmed label separately.

While the camera is enabled and speech/playback has been quiet for five seconds, selected frames may receive one structured observation at most every 15 seconds, with a three-second deadline and no backlog. Speech cancels pending observation work. This shares the existing local vision model and can consume GPU time during quiet periods. Debug adds no extra inference. The conversation still receives actual images independently. Two successful observations establish appearance; three successful absences spanning at least 30 seconds establish disappearance from view. Camera-off, cancelled or failed analysis never establishes departure. This is sampled presence by subject category/coat colour, not individual tracking, a full recording, or proof someone walked into/out of the room. Multiple similar animals and occlusion remain ambiguous.

Known pet notes are supplied through a fixed read-only Animal lookup alongside camera context, never an image-directed tool call. Colour is candidate evidence, not confirmed identity. Daily journal questions use dated, bounded records with explicit truncation and availability status; older days can be requested with an ISO date. Time boundaries use the timezone recorded by the desktop journal by default in Unmute (`NODIE_TIMEZONE` overrides it).

Fullscreen Debug shows received microphone words, assistant text, frame delivery, structured person/cat observations, recognition matches and saved events in a left-aligned live stream. It is off by default, retains at most 200 rows in memory, and can be cleared independently. It does not retain raw media or expose credentials/tool payloads. Vision debug reports only the structured categories actually requested, not a comprehensive scene description.

Deploy the backend with `NODIE_EVENTS_DIR` pointing to the desktop's `~/.config/nodie/events` directory, mounted read-only in Unmute. Browser-only event collection is not added; the desktop journal is available to the mounted Unmute voice backend, and desktop local voice uses the same store.

== General animal observations

The event detector describes any visible animal using bounded `kind` and `appearance` text fields; species and coat descriptions are not a fixed vocabulary. Dogs, birds, rabbits and unfamiliar animals use the same path as cats. Unknown species may be described as `animal`. These observations remain untrusted model output, not confirmed pet identities. Personal names and appearance facts belong in the user's private animal memories, never in source-code mappings.

The current presence tracker groups equal descriptions. It cannot distinguish two similar-looking animals, and changing descriptions can split observations. Repeated visibility is not proof of room entry or exit. Individual pet tracking and confirmed association with memory remain separate work.

== Recognition confirmation and debug styling

An explicit introduction can offer a local face or voice label. Check or correct the name spelling, then confirm or cancel using the on-screen prompt (Settings for face selection). A correction labels the same captured profile and never selects a different face or voice; neither a model statement nor a nearby person's spoken confirmation saves a label. The prompt uses the same 32 px button height, 8 px radius and spacing, and 12 px inner padding as the debug controls. In compact mode its buttons lie inside the avatar's native input region. Fullscreen debug uses consistent 24 px outer insets and a slim amber scrollbar with a transparent track; forced-colour mode preserves system scroll colours.

Enable People — faces and People — voices separately in Settings. Face matching also needs the camera enabled; voice matching needs the microphone enabled and the local diarization service healthy. This is fallible recognition of enrolled local profiles, not identification of arbitrary people from the internet. Do not interpret an empty profile list as a malfunction before enrollment.


== Visual curiosity

Desktop Unmute mode can initiate a brief, image-grounded question about a stable visual change. Settings offers Off (default), Debug observations only, Low, Normal and More often. Low permits people-count increases and animals; Normal also permits newly held objects. Model-generated observations use generic categories, not household-specific identities. A visible cup does not establish coffee or ownership. Local batch voice and browser-only event collection remain unsupported.

Two successful observations at least five seconds apart establish changes. Camera startup establishes a baseline rather than announcing everything already present. Failed analysis is not absence. Objects depicted on screens are excluded when flagged; this is fallible visual evidence, not reliable tracking or identity recognition. Observation descriptions never become instructions.

Delivery waits at least 60 seconds after camera/session startup and 20 seconds after voice activity. The event journal must be enabled and the camera, microphone and speaker must be on, playback idle, and no introduction confirmation open. Each event retains the exact originating image and expires after 20 seconds. A backend gate independently requires the waiting-for-user state, a high pause prediction and 20 seconds without words. The generated question enters assistant history normally; no invented user utterance or image is written to history.

Low uses a ten-minute minimum gap and six daily questions; Normal uses four minutes and fifteen; More often uses 90 seconds and thirty. A topic type has a further 30-minute cooldown, and the same category is suppressed for 24 hours. At most one question is delivered without another user utterance. Unanswered questions double the gap; two pause curiosity for an hour. An interruption pauses it for fifteen minutes. A response within 30 seconds is treated as engagement, not proof that the question was answered semantically.

Questions cancelled before delivery release their reservation without penalising the user. An owner-only, bounded text ledger in the events directory reserves delivery before speech, preserving repeat suppression across crashes and restarts. Clearing the event journal clears this ledger too. No images or spoken answers are saved there. Existing scene-context tool isolation still applies: curiosity cannot authorize memory writes. Debug shows candidates, deferrals, expiry, budget decisions and response outcomes. The model chooses its own words; there are no canned spoken questions.


== Recognition performance and identity links

The face worker verifies and loads models once per worker lifetime, processes one bounded selected JPEG at a time and is killed on cancellation or deadline expiry. The next frame starts a replacement. Camera shutdown releases the worker; status polling and repeated observations do not rewrite profiles, and saved `lastSeen` updates are throttled to once a minute. A synthetic bundled-portrait check measured 343 ms cold and 36–44 ms warm on the local CPU; this is not household accuracy or end-to-end latency validation.

Settings provides explicit shared-person links between enrolled face profiles, voice profiles and an existing Person memory. After confirming a face introduction, “Link this face to a person and memory” opens that form with only the exact saved face selected. Choose an existing person or a new display name, then select the voice and memory links and confirm separately. Equal names never select a person, voice or memory automatically; a previously confirmed association can reopen its existing person. Removed profiles cannot be replaced with a namesake, and switching people clears unrelated face/voice selections. Saving an introduction alone does not create memory or identity links. No face/voice association is inferred from co-presence. The next conversational response can retrieve a bounded relevant brief through that confirmed mapping, while keeping the current recognition uncertain.

== Voice introduction confirmation

An explicit self-introduction for a sole, unambiguous sampled voice opens Settings. Check the bounded heard-text excerpt, correct the name spelling and click “Confirm voice and name”. The proposal remains tied to the captured voice; nearby faces and matching names do not select identities. Ambiguous, multi-speaker, uncovered and cross-speaker introduction samples cannot offer a label. Cancel, expiry or closing Settings discards the pending excerpt/name. A confirmation deadline releases a stalled UI and asks the user to check saved profiles because a delayed backend write may still complete.

After a successful save, “Link this voice to a person and memory” opens the existing linking form with only that exact saved voice selected. Person, face and memory links require a separate explicit confirmation. No new voice model, microphone, recording or automatic association is added. The excerpt is ephemeral Settings data and is not written to the journal or recognition profile; normal text transcript retention remains independent.

Fullscreen Debug groups adjacent completed words from the same possible voice match into speaker phrases. Named matches are labelled “Possible match”, unnamed matches “Unknown voice (possible match)”, and overlap, missing coverage or other insufficient evidence remains “Unattributed”. Labels can change when later evidence arrives. A name accompanying an unattributed word is not persisted as its speaker. This remains fallible diarization, not verified identification; live household introductions and accuracy checks remain necessary.

== Guided recognition calibration

Settings > Recognition calibration adds samples to an already named face or voice profile. Choose the recognition type and exact profile, then capture another sample or run “Test recognition only”. Calibration does not enroll unknown identities or create person/memory links. Existing links retain their profile IDs when a sample is added.

An explicit face capture reuses the active camera preview and sends one bounded JPEG directly to the existing face worker; it does not invoke scene-description inference. Only one detected face with a sufficiently large, sharp, isolated crop is eligible. The temporary 96×96 crop is shown for confirmation. Try slightly different views or lighting; duplicate samples and samples that fit another named profile better are rejected. At most four face samples per profile are saved.

Voice capture reuses the existing enabled microphone stream for a four-second recording. Conversation transport (or the local recorder) pauses for that capture and is restored without opening another microphone or changing the mic/speaker settings. Device shutdown, cancellation or assistant playback invalidates the sample. The local diarization service must find one speaker, at least 2.5 seconds of clean speech and consistent segment coverage. At most eight voice samples per profile and 64 total voice samples are retained. Use varied spoken phrases, not simultaneous introductions.

Quality and analysis latency appear in Settings and text-only Debug. Match similarity is an embedding comparison, not an identity probability. Testing uses existing named profiles without adding candidates, saving embeddings, updating `lastSeen`, or writing either recognition store. A possible match remains fallible. Collection stores only a confirmed normalized embedding, never the camera image or audio; pending embeddings/crops remain in memory for at most 60 seconds. Closing Settings, cancellation and expiry discard them. A save that cannot be confirmed asks the user to check sample counts rather than retry blindly. Analysis has a three-second deadline, capture/submission a ten-second deadline and no backlog. Normal matching and curiosity are suspended while calibration is pending. Household accuracy remains unmeasured until real introductions and repeated tests are performed.


== Actual images in local voice

Local voice reuses the opt-in camera and selected-frame pipeline. Before submitting an audio turn it requests a fresh selected JPEG, waiting at most 350 ms for capture and another 100 ms for delivery. It never enables an off camera or opens another camera. The selected image goes directly to the configured `LOCAL_LLM_MODEL` through Ollama's native `images` message field, adjacent to the current question. No separate image-description model or background conversational inference is started. See https://docs.ollama.com/api/chat[Ollama chat API].

A snapshot is at most 512 KB and ten seconds old when sent to the model. Images are ephemeral reference data and never enter conversation history, transcript files, diagnostic logs or returned voice-turn results. Camera ON/OFF is independent of image availability. An expired or missing snapshot means “camera on, fresh image unavailable”, not “camera off”. Debug reports the capture timestamp actually used, camera-off, missing image or unsupported model; the preview tooltip now reflects snapshot availability in local mode too.

Desktop delivery uses trusted IPC; browser delivery uses a same-origin, loopback-host-checked POST with a three-second upload deadline and bounded JSON body. A server-issued camera lease and increasing revisions reject delayed uploads from earlier camera states or renderer sessions. Delivery retains one in-flight update and only the latest pending update; camera-off bypasses stalled acknowledgements and discards queued images. Three-second handshake/delivery deadlines bound waiting; a failed handshake releases readiness for retry. Before model inference, freshness and device state are checked again. Camera-off aborts an image-bearing turn; the renderer also drops late visual replies if the camera was switched off or reopened before playback.

Visible text remains untrusted. Image turns expose only the final-reply tool and reject model-requested control, naming and other tools at execution. Fixed read-only node snapshots requested by the microphone transcript remain available. Spoken window/device controls still use the existing independently checked microphone transcript. A direct plain-text visual reply is final, avoiding the existing text-mode second model pass and ensuring image expiry during generation does not erase a valid answer. Ordinary read-only memory recall remains available; no visual memory-write tool is added.

An explicit unsupported-image provider response retries once without pixels and caches the limitation for five minutes per endpoint/model. Unrelated provider errors are not treated as missing vision. The model receives the precise unsupported capability state, rather than guessing that the camera is disabled. This needs an image-capable conversational model; it does not infer identities from appearance or replace face recognition.

=== Validation and performance limits

All 360 unit tests pass, including actual same-origin/invalid/oversized HTTP checks, expiry, camera-off cancellation, latest-only delivery, stale leases/revisions, handshake recovery, no image persistence and image-driven action rejection. A browser check used a generated canvas video stream through the actual camera selector, browser bridge, scene transport, local turn and Debug/tooltip code. No camera hardware was accessed.

An actual local synthetic speech → transcription → image/model → speech synthesis check asked “What colour is the mug in this picture?” about a generated red mug and received “The mug in the picture appears to be red.” It used one model call and stored no image in history. The turn took 20,686 ms: transcription 198 ms, model 19,903 ms and speech synthesis 575 ms. This single check is functional evidence, not a latency or visual-accuracy guarantee. A subsequent GPU check showed 23,099 MiB used of 24,576 MiB and another model loaded; concurrent service use complicates attribution. Live household detail/recognition accuracy and sustained performance remain unvalidated. This PR removes an extra visual inference pass but does not solve shared GPU contention.
